## 2. 产品结构建议

保留既有五入口，明确二级职责；这是对现有方案的建议性细化，不静默替换总体规格。

| 一级入口 | 二级组织 | 核心动作 |
| --- | --- | --- |
| 今天 | 我的今天、课表、课程、任务；首页保留直达课表/课程入口 | 看下一项安排、处理截止、进入课程；同意后将已确认参与的活动写入个人日程 |
| 校园 | 搜索、交通、吃喝、自习/设施、学院与部门、校园服务、社团 | 找准一个对象，查看事实和适用条件，完成导航/办理/收藏 |
| 发现 | 活动、学习组队、校园墙、圈子；校园/全港范围可切换 | 找到合适的事情，了解条件，自愿参与 |
| 消息 | 行程与服务变化、活动通知、互动；私信请求在对应阶段启用 | 处理与本人有关的变化，控制通知，不靠红点驱动使用 |
| 我的 | 学校资格、连接与授权、我的参与/发布、收藏、隐私 | 管理自己的身份、资料与行为 |

“今天”是个人摘要，课程页有完整的资料/任务/学习协作结构；不能把学习压缩成首页一张卡。“校园”主要解决查找与办理，“发现”主要解决遇见内容和参与活动；两者引用同一个地点、社团或活动记录，不分别维护副本。

全局搜索按课程、地点、路线、服务、组织、活动分组，私人结果只在本人获准范围内返回。第一版可用普通关键词和别名，AI 问答后续基于相同来源和权限读取，不另建无法追溯的事实库。

## 3. 从信息走向行动

地点详情建议从上到下：名称/类型/已核验图片；位置、开放规则、适用人群；导航/收藏；有来源的设施特征；相关活动和用户经验；纠错与来源更新时间。各类型采用不同主要字段，不强迫所有对象使用相同大图片模板。

- 食堂：开放时段、价格信息的来源与日期、导航、用餐经验，允许主动发起饭搭子邀请。
- 自习地点：开放规则、安静要求、插座等已核验信息、如何预约、相关学习招募。没有实时座位来源就不显示“目前空闲”。
- 校巴路线：方向/站点、运行日期与资格、计划班次或明确来源的预测、来源更新时间；不套用地点评分布局。
- 课程：课程基本信息、本人任务/资料引用、获准讨论与组队；正式选课及作业状态须有真实授权。
- 社团：组织介绍、官方联系与入会方式、活动、关注；有独立公开入口，但不重复创建活动。
- 学院/部门/教师：公开专业信息与官方联系路径；第一版不建立教师个人打分榜，不聚合私人联系方式。

关键连接：课程→学习招募→地点→报名/确认→个人日程；地点→相关活动→报名；社团→活动→成员主动关注。所有自动保存或共享行为都应有明确选择，不能公开用户课表或将浏览行为显示为参与。

具体示例（设计场景，非当前供给）：用户查某自习室→确认开放规则→看到周四三人安静自习邀请→了解时长、语言、人数与取消方式→报名获确认→本人选择加到日程→收到活动变更。没有真实招募时显示创建入口或暂无，不伪造人数、评价和活动。

## 4. 视觉与操作调整

- 借鉴分类、搜索、照片与详情结构，使用原创视觉与获准校园图片，不复制其图标和品牌。
- 氛围图适合校园探索页；查车、DDL 与办理页优先显示任务信息。不同页面不统一塞大背景。
- 截图里部分描述被截断且类别重复出现；列表优先展示地点差异，如开放规则、楼层、用途，长说明放详情。
- 浅深色模式跟随系统并核对对比度；不能仅反转颜色。截图展示两种模式不证明全部可读性已通过。
- 评分显示样本数与日期，少量评价只作经验展示；规则和开放时段不能被评论内容覆盖。
- 社交始终可选，查看校园信息不要求发帖、公开资料或分享日程。

## 5. 对实现与现有 API 文档的影响

以下是我们的建议设计，不是从截图推断出的竞品技术架构：

以已有的 Institution、Source、Course、Place、Service、Route、Circle、Activity、Participation、Post 为基础；新增或细化 Organization/Department、公开专业 StaffProfile、Review、Bookmark、Correction。后台先由一个应用和数据库承载清晰模块，不为分类数量拆成多套微服务。

每个对象应有稳定 ID、学校/校区/可见范围、别名、来源与更新时间。官方事实、运营核验内容、学生经验分别标记。学校受限活动不因分享就变公开；无权查询的内容不进入搜索摘要。多校扩展通过学校数据与权限配置完成。

现有 [API 文档](../api/super-app-api.md)中的列表与来源可以继续使用；完整原生登录合同之外，还需评审地点详情、目录、收藏、评价/纠错、全局搜索、按对象查询相关活动、社团管理及招募写入。路径和字段在模块设计后补入 OpenAPI，当前 48 个拟议操作不等于已覆盖这些新增范围。

运营后台首期优先显示过期来源、待核验时刻、活动变更、举报和待处理纠错；用户与设备总数是辅助统计。后台权限按工作职责限定。

## 6. 建议验证顺序与交接

下一次原型聚焦五个关键页面：今天、校园目录、地点详情、课程详情、活动/学习招募详情与加入状态。以查车、找地方学习、查一门课并组队三条任务观察用户能否理解；地点页和课程页都要能进入真实相关活动，空状态可操作。

完成上述闭环后再扩充广泛内容目录、评价和校园墙形态。学生端继续 iOS 优先；官网承担公开分享与下载，后台承担维护。没有必要因竞品宣传多端就增加本轮安卓/Watch/桌面客户端范围。

本轮完成：六图证据拆解、官网交叉核验、五入口细化、对象详情与学习/社交连接、API 缺口登记。未执行：竞品私有功能实测、移动 UI 或后台实现、现有 OpenAPI 扩展。参考结构值得作为设计输入，留存与社交效果仍需真实试点验证。
